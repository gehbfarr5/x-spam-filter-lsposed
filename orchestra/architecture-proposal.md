## 关键词资产方案（已有充分证据，风险点需要用户过目）

- **来源**：固定到 ZPVIP/x-spam-filter commit `9cf7cc1`（2026-08-16）的 `keywords.txt`，
  184 条纯文本关键词，**Apache-2.0**。复制到本项目需要：①附 Apache-2.0 全文到
  `THIRD_PARTY_NOTICES.md`；②记录来源仓库/文件/固定 SHA/下载日期；③如果我们改动过列表，
  要显著标注"modified from ZPVIP/x-spam-filter"。不引入 amahteru/x-comment-blocker 那份
  755 行的 MIT 社区列表（用户只要求参考 ZPVIP 这一个仓库，范围克制）。
- **⚠️ 需要你确认的风险点**：研究发现 ZPVIP 原项目里不少关键词很宽泛（`男大`、`女仆`、
  `超可爱`、`纯情`、`同城` 等），而且**原项目的过滤范围是有意收窄的**——只作用于"推文详情页
  的回复"，明确排除主推文，就是为了避免这类宽泛词把正常推文也匹配掉。
  我们已确认的需求是"四个区域统一生效、完全隐藏、不做独立开关"，如果直接照搬这 184 条词，
  **可能会把不少正常推文也隐藏掉**（比如提到"同城"的普通闲聊、提到"男大女大"的普通吐槽）。
  这不是要推翻你之前的决定，只是这条证据值得你知道后再拍板——三个选项见下面的 AskUserQuestion。
- **匹配算法**（复用原项目思路，不复用其 DOM 实现）：包含匹配（非整词），统一转小写，
  去除空格/零宽字符/方向控制字符做归一化（应对"同 城"这种拆字规避），普通词和用户后续
  可能加的正则分开处理。这部分照抄逻辑没有技术分歧，不需要用户选择。

## Hook 点技术方案对比

### 方案 A（推荐）：Hook 数据模型/JSON 解析层

**做法**：在 `com.x.models.timelines.items.Urt*` 系列（新，kotlinx.serialization）和/或
`com.twitter.model.json.timeline.urt.Json*`（旧，LoganSquare）这两条数据模型链路的
"条目列表已经解析出来、还没交给 UI"的位置插入过滤：拿到每个 entry 的正文文本
（`PostResult.getText()`/等价字段）跑关键词匹配，命中就把该 entry 从 `List` 里剔除。

**证据支撑**：
- 两条链路的类名和字段/JSON key 映射在 12.17.0 里完全未混淆（序列化框架强制保留），
  相比 UI 层的单字母混淆类名，**跨版本升级抗性显著更强**——不需要像 TikTok 项目那样
  每次发版重新做特征匹配。
- 已有静态证据显示搜索的 9 个子 Tab、通知页都复用同一套 `Urt*` 时间线模型，
  **一次 hook 有较大概率能同时覆盖时间线+搜索+通知三个场景**（评论区还需运行时验证）。

**尚未闭环的地方**：新旧两条链路具体谁负责哪个场景、以及"entries 列表最终交给 UI 前"
精确是哪个类哪个方法，静态反编译没能穷尽（那样做收益递减、耗时会很长），需要 P1 阶段
在真机挂探测性 `XposedBridge.log`，实际操作四个场景抓真实调用路径来锁定。

**风险**：如果 X App 真的存在"部分场景走新链路、部分场景走旧链路"的情况，可能需要同时
挂两处 hook 才能覆盖全部四个区域，工作量比单一 hook 点略高，但仍远低于方案 B。

### 方案 B：Hook UI 层 Adapter/ViewHolder 的 bind 方法

**做法**：类似 TikTok 双击评论/Post Blocker 项目的路子，直接在 RecyclerView Adapter 绑定
数据的地方判断文本、跳过/移除该 item。

**证据支撑**：离渲染最近，理论上误伤面最小（只影响"要不要显示"，不碰缓存/已读计数等
其它消费同一数据的逻辑）。

**问题**：
- P0 侦察中抽样到的 UI 层类大量是单字母/极短名（`f`/`g`/`x`/`z`/`di`/`k` 等），
  且 X App 体量、迭代速度都明显大于 TikTok（17 个 dex、17.0+ 大版本号），
  这类短名符号在每次发版都可能轮换，历史经验（TikTok 系列）显示这种打法要持续投入
  "重新反编译+重新定位锚点"的维护成本。
- 四个场景（时间线/搜索/评论/通知）大概率是四套不同的 Adapter/ViewHolder，
  等于要维护 4 组独立的、易失效的 hook 点，而不是方案 A 里可能共享的 1-2 个锚点。

## 推荐

**方案 A**，理由：版本抗性强、维护成本低、有较强证据显示能一次覆盖多个场景，
与本机既有项目（RedReader/TikTok）积累的"优先选语义稳定锚点"经验一致。

**下一步（P1 第一阶段，实现前必须做）**：不是直接写 hook 代码，而是先在真机装一个
"只打日志、不做任何拦截"的探测模块，挂在方案 A 涉及的候选类构造函数/关键方法上，
实际操作时间线/搜索/评论/通知四个页面，用日志证据锁定：
1. 每个场景实际命中哪条链路（新/旧）、哪个具体类；
2. "entries 列表交给 UI 之前"的精确注入点。
确认后再写真正的过滤逻辑，避免在错误的假设上返工。
